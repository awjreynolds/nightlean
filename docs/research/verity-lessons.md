# Verity lessons for Noctium

Research snapshot: 16 November 2026. Upstream source: `lfglabs-dev/verity` at `2b63b08f1adc25631b9e45b40b6206eeda3fd934`. Every upstream source link below uses this immutable revision. Noctium is the project name. The workspace and Lean modules still use `nightlean` and `Nightlean` during the rename.

## Assessment

Verity is a useful reference for scaling a Lean compiler proof stack. Its strongest transferable ideas are explicit proof-supported fragments, reusable semantic interfaces, small contract-specific instantiations, and generated trust reports. Its Ethereum execution and storage models do not fit Midnight. The inspected repository implements a Lean embedded contract language, a Solidity importer, and an Ethereum compiler through Yul and trusted solc. [Upstream overview](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/README.md#L9-L45)

Recommendation: finish Noctium's current scalar preservation and deployment binding packages. Apply the lessons at those existing boundaries. No replacement compiler architecture or extra intermediary language follows from this research.

Links for in-progress implementation modules point to their owning issues until those modules are published.

This report distinguishes upstream claims from inspected definitions and theorem statements. Source inspection establishes the statements and implementation shape. I did not rebuild Verity, replay its complete proof closure, or qualify its deployed bytecode. The findings below are architectural research, not a security audit.

“Zero axioms” needs qualification. Verity's registry means zero project-level Lean axioms. The population audit allows `propext`, `Classical.choice`, `Quot.sound`, plus enumerated native-evaluation origins and runtime compiler overrides. These include concrete native lowering witnesses. The registry explicitly classifies native code generation as a trusted reduction boundary. This differs from Noctium's accepted proof policy, which rejects all native-computation axioms. [Registry explanation](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/docs/AXIOMS.md#L178-L213), [actual population allowlists](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/scripts/VerityUnionAxioms.lean#L103-L141), [Noctium policy](../development/proof-registration.md#independent-model-pin-and-fresh-replay)

One source comment deserves particular care. `BytecodeTranslationValidation.lean` says its certificate removes solc from the trusted base. The inspected checker compares two supplied `Nat` digest fields, checks a nonempty block interval and optionally checks jump-destination membership. Its soundness theorem concludes precisely those facts. The certificate carries no Yul execution relation, EVM execution relation, or derivation connecting either digest to execution. This module alone therefore supplies no semantic removal of solc. The README and trust document correctly retain solc. This is a lesson about interpreting theorem conclusions, not a claim of an exploitable vulnerability. [Certificate and checker](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/Proofs/YulGeneration/BytecodeTranslationValidation.lean#L125-L187), [broader source comment](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/Proofs/YulGeneration/BytecodeTranslationValidation.lean#L20-L43)

## Ranked lessons for the current implementation

### 1. Adopt now: make each assurance role name its exact proposition

Keep frontend identity, compiler preservation, application policy, completeness, privacy, bytes and deployment binding as separate obligations. Verity's body-equality generator and bytecode digest certificate demonstrate why theorem names and green builds do not establish a broader advertised property. The native final theorem also shows how a semantic premise survives composition even when no custom axiom appears. Sources: the frontend, certificate and final-theorem links above.

For issue 64, retain both required roles in [ScalarExportAudit.lean](https://github.com/awjreynolds/noctium/issues/64). [ScalarTranslation.lowerCircuit_sound](https://github.com/awjreynolds/noctium/issues/64) already concludes an actual successful source run and exact input, public-group and return agreement from arbitrary satisfying assignments. Finish actual-lowerer witness completeness through [ScalarLowering.lean](https://github.com/awjreynolds/noctium/issues/64), including fresh names, aliases and CSE. An accepted validator rejecting extra legitimate witnesses would still satisfy soundness. Do not infer completeness from acceptance alone. The [current scalar research](https://github.com/awjreynolds/noctium/issues/64) records this unfinished package.

For issue 57, extend the existing qualified artifact chain into [deployment_audit.rs](https://github.com/awjreynolds/noctium/issues/57). Require the authenticated network, contract address, operation, key identity and initialization context to join the independently checked artifact package. These are existing work surfaces, not new tickets. Preserve the distinction between evidence for native key generation and a kernel theorem about its implementation.

### 2. Adopt now: connect support checks to semantic interfaces

Verity makes exclusions fields of `SupportedFunction` and `SupportedSpec`, and supplies an executable fragment checker with a theorem from acceptance to fragment membership. Its support-profile module factors optional capabilities and bridges older predicates. The transferable pattern is a checked interface for each qualified subset. A capability bit alone proves no execution property. [Fragment checker and soundness](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/Proofs/IRGeneration/FragmentCheck.lean#L17-L44), [soundness theorem](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/Proofs/IRGeneration/FragmentCheck.lean#L97-L112), [support profiles](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/Proofs/IRGeneration/SupportedSpec/SupportProfile.lean#L9-L54)

Use Noctium's existing [NativeExpected](../../Nightlean/Backend/NativeExpected.lean), [NativeProducer](../../Nightlean/Backend/NativeProducer.lean), [ScalarValidation](https://github.com/awjreynolds/noctium/issues/64), [Target](../../Nightlean/Target.lean) and [native feature matrix](../compatibility/zkir-feature-matrix.json). For each future native construct, attach source semantics, target relation, lowering/validator proof, privacy rule and artifact identity before describing the construct as proof-qualified. Keep availability on ZKIR 3.2.0/3.2.1 and ledger 9 separate from proof qualification. Issue 43's guarded lowering and issue 44's composite disclosure retain their own admission boundaries. No generic capability framework is needed to finish issue 64.

### 3. Already doing: retain independent artifact and assumption audits

Verity's axiom auditor traverses actual declaration types, bodies and inductive constructors, fails on unresolved dependencies, and rejects an empty population. Its runtime override checks also track `implemented_by`, `extern` and `csimp`. These are useful audit controls even when proof terms themselves elaborate. [Auditor contract](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/scripts/AxiomAudit.lean#L32-L77), [override inspection](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/scripts/AxiomAudit.lean#L361-L425)

Noctium already has a stricter data-only kernel/statement/axiom audit and independent source-to-byte qualification. Preserve [ArtifactBytes](../../Nightlean/Verification/ArtifactBytes.lean), [ArtifactCertificate](../../Nightlean/Verification/ArtifactCertificate.lean), [ExportAudit](../../Nightlean/Verification/ExportAudit.lean) and [AuditArtifactExport](../../scripts/proofs/AuditArtifactExport.lean). Issues 56 and 58 are closed for the qualified PrivateClaim package at immutable source `925164d0e17d994038d77d3b2b71c410619557d3`, with explicit parser/native/crypto assumptions. They are not missing foundations to rebuild. [Retained qualification and scope](../development/private-claim-artifact-certificates.md)

Do not adopt Verity's native-evaluation exceptions. Keep only Noctium's three approved foundational axioms. Treat compiler overrides and host execution as provenance/model-agreement boundaries, regardless of the logical axiom list.

### 4. Already doing, extend carefully: name the observer before claiming privacy

Verity's final result relation explicitly selects observed slots and events. A separate `Obs` record describes status, return bytes, logs and storage. These are useful examples of making observations explicit. The inspected relations compare executions across compilation layers. They are not two-run secrecy statements about different private witnesses. [Final observer](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/Proofs/EndToEnd/Base.lean#L71-L94), [observation record](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Verity/Specs/ObsAlgebra.lean#L49-L75)

Retain [NativePrivacy.Policy and Observation](../../Nightlean/Verification/NativePrivacy.lean), [Disclosure](../../Nightlean/Disclosure.lean) and issue 44's [ComponentDisclosure](https://github.com/awjreynolds/noctium/issues/44). The existing PrivateClaim theorem covers successful valid executions with equal declared public context and explicit exclusions. Failures, timing, proof bytes and host/provider observations require separate obligations. Preserve the established failure-channel counterexample when extending the source language. Functional correctness, a constant public return, and a zero-knowledge proof system each leave other disclosure channels unresolved. [Current privacy scope](../development/private-claim-native-privacy-proofs.md), [source failure counterexample](../development/proof-registration.md#privacy-scope)

### 5. Adapt later: generate an audit status view from existing evidence

Verity renders `proved`, `assumed` and `unchecked` buckets and localizes trust surfaces to usage sites. Its workflow regenerates inventories, builds the axiom audit and publishes reports. The useful feature is visibility of the exact boundary, rather than a theorem total. The metrics implementation derives a “proven” count from manifest totals and placeholder counts, so that statistic is not an end-to-end semantic guarantee. [Status rendering](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/CompilationModel/TrustSurface.lean#L1021-L1074), [usage sites](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/CompilationModel/TrustSurface.lean#L1332-L1346), [CI checks](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/.github/workflows/verify.yml#L504-L531), [metric derivation](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/scripts/verification_metrics.py#L145-L177)

After issues 64 and 57 settle, derive one compact view from the existing proof receipts, required theorem roles, feature matrix and portable artifact schema. For each role, show the source/artifact revision, checked proposition, admitted feature set, observer and unresolved premises. Link [proof registration](../development/proof-registration.md) and [portable artifacts](../development/portable-artifacts.md). Avoid another manually maintained progress ledger. A report's `proved` label must come from accepted evidence for the required proposition.

### 6. Adopt now within ongoing proofs: small semantic APIs and fixed statements

Verity's agent guide asks for reusable step equations, frame lemmas, limited import dependencies and focused proof modules. Its architecture guide separates generic lemmas from small instantiations. These are useful development practices. The guide's speed claims and custom accelerator prescriptions were not benchmarked here. [Proof architecture guidance](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/AGENTS.md#L157-L188)

In issue 64, keep small lemmas for cache hit/miss, fresh assignment, bound propagation and emitted instruction meaning. Continue using the existing [ScalarNormalizationSoundness](https://github.com/awjreynolds/noctium/issues/64), [ScalarInstructionEncoding](https://github.com/awjreynolds/noctium/issues/64) and [ScalarLowering](https://github.com/awjreynolds/noctium/issues/64) seams. Preserve the required theorem statements during decomposition. Split proof files when import cost or maintenance warrants the split. Do not introduce a new accelerator stack or enforce an arbitrary line-count limit to finish this package.

## What not to copy, and questions left open

Do not copy Ethereum's 256-bit wrapping arithmetic, hashed storage-slot layout, ABI dispatch, gas or reentrancy assumptions into Midnight. Verity's own mapping history illustrates the danger: global injectivity from pairs of 256-bit words into one 256-bit word was replaced with finite-footprint non-aliasing premises. The transferable lesson is to state scoped cryptographic/layout assumptions. Noctium needs its native field, ledger-state and cryptographic definitions. [Finite-footprint correction](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/docs/AXIOMS.md#L88-L123)

Do not use Compact as the target architecture or reduce the full native roadmap to another compiler's supported subset. Retain the Lean frontend, typed IR, semantics and primary lowering, native ZKIR/ledger targets, and Rust proving/funding/submission/recovery path. This is a Noctium design constraint, not an inference about Verity.

Three upstream questions matter before relying on stronger claims:

1. Which theorem removes `hUserBodyResult` for arbitrary supported compiled bodies? The inspected generic theorem requires the premise, and the source explicitly identifies generic native body simulation as missing. [Remaining obligation](https://github.com/lfglabs-dev/verity/blob/2b63b08f1adc25631b9e45b40b6206eeda3fd934/Compiler/Proofs/EndToEnd/Base.lean#L5439-L5442)
2. Which frontend theorem relates the actual DSL execution to the generated model for the requested feature? The generated body equality is insufficient for this role, and the macro remains documented as trusted. Sources: the frontend links above.
3. What independently checked execution semantics, whole-program coverage and artifact identity would justify the bytecode certificate's stronger comment? The inspected fields and theorem do not supply those links. Sources: the certificate links above.

No universal Verity privacy guarantee was established by this inspection. No live theorem count or CI badge was used as durable evidence. No upstream code was copied, no upstream build ran, and no Noctium implementation or ticket changed during this research.
