# Full native-capability Noctium

The active goal is full coverage of the pinned ZKIR v3 implementation and native Midnight ledger contract capabilities, with verified Compact feature equivalence as a minimum coverage check. The compiler and primary lowering remain Lean 4. Compact supplies engineering lessons, source-semantic evidence and regression ideas. It must not become a compiler, runtime, or mandatory consumer dependency, and its exposed features do not cap Noctium's scope.

The user's 2026-11-16 clarification explicitly adds native composability beyond Compact's current exposure and compiler checks for guarded disclosure of private state into public state. Existing scalar, runtime and artifact work continues under this expanded destination.

Proof-backed functional correctness and contract auditability are core delivery requirements. Authors use ordinary Lean specifications, theorem syntax, tactics and proof libraries. Circuit execution follows a finite compilable subset, while theorem authoring uses Lean's full proof language. A verified-contract claim must identify its exact specification, checked theorems, preserved compilation path, deployed artifacts and remaining assumptions.

## Delivery goals and exit gates

These six goals match the public capability graphic. Each goal requires implementation and retained evidence. A documented upstream blocker keeps the affected capability open. A successful example, a parsed instruction or a closed implementation ticket does not complete a goal.

| Goal | Required result | Completion gate |
| --- | --- | --- |
| G1. Full native ZKIR v3 | Cover every instruction and value type in the pinned implementation through typed source mappings, encodings, checking, key generation, proving and verification. | The complete native inventory has passing semantic and adversarial cases. Applicable operations have proving and ledger acceptance evidence. Deprecated operations have tested compatibility or replacement behavior. No unresolved capability blockers. |
| G2. Lean contract language | Support the required scalar and composite types, functions, modules, generics, bounded loops and guarded control. Use ordinary Lean syntax and tactics for specifications and proofs. | Every language capability in the evidence matrix passes source-to-native positive and negative cases, including combinations of features and resource limits. Compact equivalence supplies a minimum comparison. |
| G3. Ledger capabilities and composition | Support native state ADTs, cryptography, constructors, sealed fields, Kernel effects, contract calls, events and assets. | Source-generated contracts demonstrate accepted state effects, call bindings and failure behavior on the pinned localnet. Native capabilities beyond Compact's exposed surface receive their own cases. |
| G4. Private execution and disclosure | Support witnesses, host providers and private-state lifecycle. Track private value and control dependencies and require explicit authorized release at public sinks. | Positive and rejected-disclosure cases cover outputs, state writes, events and calls, including composite values and private guards. Privacy claims identify an observer, allowed releases, failure scope and host assumptions. |
| G5. Native, web and mobile SDKs | Deliver Rust, C/C++, TypeScript/WASM for web dapps, Kotlin for Android and Swift for iOS without a mandatory Node process. | Each target executes shared contract artifacts and conformance vectors. Proof, transaction, provider and private-state interfaces pass the declared target's integration tests. Runtime-only subsets stay labelled as subsets. |
| G6. Proof-to-deployment assurance | Bind actual-source specifications and proofs through compiler preservation, exact artifact bytes, keys and deployed operations. | Kernel replay, exact theorem-role checks, axiom policy, soundness and source completeness pass for the supported compilation path. Reproducible builds and public deployment audits authenticate the same artifacts and revision. Trust assumptions and independently reviewed limits accompany every verified-contract claim. |

The private one-time claim on the isolated localnet is the regression workload and first assurance case. Public-network deployment requires separate qualification. Full coverage requires all six exit gates, with no open feature rows relabelled as delivered. Research-preview milestones remain useful without implying full coverage or unrestricted compilation of Lean programs.

## POC execution priority, 2026-11-17

Prioritize native ZKIR v3 feature implementation and a complex existing contract rebuilt in Lean. The [OpenZeppelin confidential-token/public-supply port](https://github.com/awjreynolds/noctium/issues/68) is the concrete POC workload, pinned to upstream source. Use Compact as a behavioral reference, with direct Lean-to-ZKIR compilation. Compare observable results, state transitions and proof acceptance rather than requiring identical generated IR.

For each feature group, compile the changed modules and run one focused native example. Add a targeted rejection case where the new behavior needs one. Reuse existing evidence. Defer additional formal proofs, repeated export audits, broad regression reruns, cross-profile duplication and deployment repetitions unless a concrete failure requires them. Run one integrated localnet demonstration when the port reaches that milestone.

The final assurance goals above remain release requirements. They must not block POC feature breadth or consume repeated validation work during implementation. Keep support claims scoped to the checks performed.

## Baseline

The latest stable feature reference checked on 2026-11-16 is Compact toolchain 0.36.1, language 0.28.0, at source revision `7fa3a117c5e7efe9d2c51da04263e5f0b3509144`. The public-network matrix still lists 0.36.0. The newer source release bundles ZKIR 3.2.1. Noctium preserves its accepted 3.2.0 default and now provides a [selectable 3.2.1 compiler/runtime profile](../development/zkir-3.2.1-integrated.md). An isolated exact-commit build produced authenticated public bundles and finalized claim/scalar deployments and calls with matching state bytes. The earlier [experimental qualification](../development/zkir-3.2.1-qualification.md) remains separate historical evidence. These selected workflows do not qualify every capability or a public network.

The [baseline report](../research/compact-equivalence-baseline.md) and [machine inventory](compact-feature-matrix.json) contain the source register, version distinctions, observed implementation gaps, and acceptance requirements. The initial 221 entries are inventory records, not independent delivery units or a percentage-complete score. All equivalence results are unverified.

## Required outcomes

- Every type and instruction in the pinned ZKIR v3 implementation has an explicit source mapping, type/precondition rules and execution evidence, or a recorded upstream blocker. Deprecated operations receive explicit compatibility or tested replacement handling. Raw parser support is not source support or ledger acceptance.
- Equivalent contract capabilities and observable semantics across the baseline's types, expressions, bounded control flow, functions/modules/generics, private execution, disclosure, ledger ADTs, cryptography, contracts, events and assets.
- Native-ledger contract composability, including capabilities not yet exposed by Compact, qualified against actual call claims, entrypoints, keys, communication commitments, state effects and failure behavior.
- Compiler-enforced information-flow rules for both private value dependencies and private control dependencies at public outputs, ledger writes, events and contract calls. A constant public write under a private guard still requires explicit authorized disclosure. Track provider/private-state origins and classify assertion/failure side channels separately.
- Native ZKIR, ledger artifacts, proof and transaction construction, with canonical encodings and reproducible provenance.
- A host-neutral runtime and provider ABI, usable without Node by a Rust application, with qualified C/C++, Kotlin, Swift, TypeScript and portable WASM options.
- Explicit private-state and transaction failure/commit rules, bounded execution and host-capability handling.
- Feature-specific positive, negative, malformed-input, adversarial, composition, cross-host, and ledger acceptance evidence.
- Correctness proofs for internal transformations, clearly scoped external conformance, and independent review before production use.
- Contract-specific preconditions, postconditions and invariants, with proofs over the actual source definitions and explicit non-vacuity evidence. A disconnected helper lemma or a theorem of an unrelated proposition does not establish contract correctness.
- A mandatory proof/audit chain: kernel-checked proof terms, transitive axiom policy, exact theorem-statement/contract identity matching, proof/import/toolchain provenance, compiler/lowering preservation and binding to the emitted circuit, native plan, keys and deployed entrypoint.
- Audit-readable proof obligations and assumptions, including native semantics, cryptography, proving/verifying implementations and host/private-state behavior. Tests and accepted receipts supplement this chain. They do not replace missing preservation proofs or authorize an unqualified verified-contract label.
- A separate privacy specification and proof obligation for proof-qualified private contracts. Define the observer, public inputs/state/results/events/calls/transcript activity, authorized releases and validity/failure scope. Prove public observations do not reveal further private differences, then preserve that property through compilation. Functional correctness alone never implies confidentiality. Proof-byte privacy requires the proving system's stated zero-knowledge assumptions; host services, logs and timing need their own scope.

Unrestricted general-purpose Lean compilation and duplication of wallet UIs, indexer services or explorers are separate products. Missing language or native integration capabilities must remain visible in the matrix. An unavailable upstream API is a blocker to record, not a reason to declare equivalence.

## Execution tracks

1. Expand the source inventory into executable semantic cases and qualify the current toolchain profile, including the Boolean-deserialization and Jubjub key-generation patch regressions.
   Audit the complete native ZKIR type/instruction surface independently of the Compact inventory. Use source-derived preconditions and targeted proving/ledger tests to choose implementation packages.
2. Replace the mandatory JavaScript execution path with a native Rust reference runtime using the existing source-generated private-claim vectors. Define a versioned provider protocol and canonical artifact ABI. See [portable runtime design](../designs/portable-runtime.md).
3. Add bounded integers, conversions, composite values and function/control-flow facilities to the typed Lean representation, elaborator, evaluator and native lowering.
4. Complete scalar state operations, constructors and sealed fields, then collections, nested ADTs, tree operations and Kernel effects with ledger-backed tests.
5. Add the complete cryptographic, contract-call, event and asset capability set, split into bounded implementation packages with feature IDs and native evidence.
   Implement disclosure analysis over the typed source/IR before exposing guarded public effects. Learn from Compact's dependency and control-flow analysis, then justify and test any differences against Noctium's native architecture.
6. Qualify native host bindings, optional WASM execution, mobile packaging, private-state lifecycle and provider capabilities against the same artifacts and conformance vectors.
7. Finish assurance, release documentation, developer packaging and the feature-equivalence evidence audit.
   Contract proof authoring, theorem registration, kernel replay/axiom auditing and native preservation are implementation tracks throughout development. They are mandatory gates for the verified product, rather than work postponed until feature breadth is complete.

These tracks contain dependencies, not a delivery estimate. The public issue map is the source of truth for claim ownership, current blockers and implementation order.

## Present evidence

The [native private-claim POC](../development/native-localnet.md) demonstrates one source program through native ZKIR and finalized local ledger execution. The [Rust runtime](../development/native-rust-runtime.md) reproduces its state and checker preimage without Node. The [C ABI](../development/native-runtime-abi.md) also executes the claim in linked C++ and validates resumable scalar-input requests. Scoped host providers and [private journals](../designs/private-state-lifecycle.md) now have a tested transaction-bound lifecycle with private-only transport and correlated compare-and-swap. The [native C/C++ client ABI](../development/native-client-abi.md) adds proof verification, funding, approval, submission and durable recovery for the qualified localnet claim. The [typed source-witness subset](../development/typed-witness-qualification.md) adds immutable-source proof, native Rust/C++ execution and finalized localnet evidence on both profiles. Durable storage and truthful acceptance evidence remain host assumptions. Full witness-language coverage, mobile/WASM SDKs, full feature parity and complete formal verification remain outstanding.

The [scalar slice](../development/unsigned-localnet.md) implements source-backed unsigned bounds, conversions, canonical ABI values and native range constraints. Thirty-four raw-witness cases pass against both qualified checker releases. The Rust-assembled integer contract has finalized local deployment/call and exact state-byte evidence. Nominal aliases, additional scalar operators and full feature equivalence remain outstanding.

The mandatory [scalar disclosure pass](../development/disclosure.md) tracks private value and control origins at current public sinks. An authorized-release native proof binds every tested public field. This is scoped data-flow enforcement, not a theorem covering failure, timing, host logs or every future native primitive.

The [native producer gate](../development/native-producer-safety.md) validates every currently emitted scalar relation before artifact emission. Its registry names all 47 instructions and 15 native value types, now registers 38 opcode names with restricted Native, bytes, typed Boolean, Jubjub including typed scalar storage, and scoped Secp/Curve25519 transport, arithmetic and scalar storage paths and rejects unsupported entries. The [current source snapshot](zkir-feature-matrix.json) records the precise coverage limits. Sixty-five producer cases and targeted native observations cover current typing, range, SSA, assertion, output and public-binding rules. Formal source-to-native preservation remains separate.

Circuit efficiency has no matched Compact baseline yet. Recorded confidential-token circuits range from K=7 for `totalSupply` to K=16 for `transfer` and delegated spending. [Issue 74](https://github.com/awjreynolds/noctium/issues/74) tracks equivalent-contract K/row comparisons on the same native profile, followed by measured optimizations. Lean implementation, opcode coverage and compilation time do not establish smaller circuits or faster proving.

[Byte ledger storage](../development/byte-storage.md) extends scalar state to Source Bytes0 through Bytes1024 in direct cells, map values and nested leaves. Native FAB alignment retains exact lengths and trailing zeros. Empty byte cells remain explicit ledger values with no native payload fields. Source checks, canonical runtime decoding and guarded defaults retain the existing disclosure and key restrictions. This adds no opcode and establishes no new proof or deployment qualification.

[Scalar byte decoding](../development/scalar-from-bytes.md) exposes arbitrary bounded byte inputs to the existing native `from_bytes` operation for Native and JubjubScalar. Reduction uses the full little-endian input modulo the target field. Empty operands evaluate before typed-zero erasure, including their assertions. The source fixture, native checker and shared host/control routes cover both fields, maximum length and retained 32-byte behavior. Typed signature helpers now have their own scoped implementation evidence. Complete compiler preservation remains separate work.

[Ordered transient hashing](../development/transient-hash.md) exposes zero through 1024 raw Native inputs to the existing `transient_hash` opcode. The compiler inserts no protocol domain or serialization fields, shares equivalent legacy three-field computations and retains cached operand assertions. Native and host/control checks pass. Primary source confirms the pinned Schnorr message is a Native-field vector and its preimage is four point coordinates followed by those fields. The resulting [typed signature helpers](../development/signatures.md) now expose ECDSA, Schnorr, Ed25519 and Ethereum address derivation through existing native operations. Their focused vector checks do not establish full signature or compiler assurance.

The [composite type foundation](../development/composite-types.md) defines nominal/structural identity and checked layouts with proof-linked leaf, logical-expanded and retained-node bounds. [Checked aggregate values and codecs](../development/composite-values.md) now preserve logical identity through Rust/C++ wire round trips and produce a native proof for the nested typed fixture. Chained index bounds remain enforced, including zero-leaf elements. [Component-aware helper outputs](../development/component-disclosure.md) now compile to checked native scalar leaves with disclosure enforcement.
